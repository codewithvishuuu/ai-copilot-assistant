## Decisions log

| # | Decision | Why |
|---|---|---|
| D1 | No privileged Discord intents; threads fetched via REST on demand | Least privilege; no Message Content intent needed |
| D2 | SQLite + FTS5 only (no vector DB, no embeddings) | Local-first, RAM-frugal, dependency-light; trade-off documented in RAG.md |
| D3 | Model `gemma4:e2b` (already present) — final confirmation after Phase 0 benchmark | Vision-capable, edge-optimized; must fit 7.8 GB RAM in practice |
| D4 | Thinking mode OFF by default; JSON-schema-constrained output | Deterministic extraction, lower CPU/latency budget |
| D5 | Single sequential inference worker | One CPU-loaded model; predictable memory and rate behavior |
| D6 | Migrations = `schema.sql` blocks parsed by `user_version` | One source of truth for schema history |
| D7 | No aiosqlite: stdlib `sqlite3` via `asyncio.to_thread` + one connection + lock | Zero extra deps; teaching-friendly |
| D8 | Headless `ollama serve` started manually for dev; user can stop it anytime | Tray app server was down/crashed; needed for live verification |
| D9 | Queue capacity counts only *pending* jobs; the active job is accounted separately | The single worker must never block itself; `/cancel` and capacity stay predictable |
| D10 | Duplicate detection = FTS5 BM25 lexical only, labeled "possibly related (not verified)" | No embeddings/vector DB on an 8 GB CPU machine; precision over recall |
| D11 | Worker treats any post-job `_stopping` as cancellation (explicit re-raise) | CPython 3.11 `asyncio.wait_for()` can swallow an external cancel when the job task finished in the same loop tick — caused a real shutdown deadlock; fixed with a regression test |
| D12 | `MAX_CHARS` default kept conservative (24000) until demo-machine profiling | CPU inference at ~16–28 tok/s punishes oversized prompts |
| D13 | Mention-first chat with the privileged Message Content intent **off** | Discord exposes text only for mention/DM/own messages; resolved replies to the bot are handled (or get a rate-limited hint when unreadable) |
| D14 | Chat context is volatile, keyed by `(guild, channel, user)`, bounded by turns/chars/TTL/LRU | No schema change in this phase; strict cross-user and cross-channel isolation |
| D15 | Chat is serialized by its own single-in-flight gate + per-user cooldown instead of the inference queue | Keeps chat responsive without consuming queue slots or the 60 s queue cooldown; revisit when scheduling is unified |
| D16 | Conversation memory persists in SQLite (`conversation_turns`, migration 3), scoped per `(guild, channel, user)`; the bounded in-memory store is only a fallback while the database is unavailable | Survives restarts without any cache resurrecting cleared or expired turns (reads are DB-first); a failed write degrades visibly in logs and is reported `persisted=False`, never silently |
| D17 | `/clear-conversation` skips deletion while the caller's scope has an in-flight reply, deletes the database rows first (single statement), and only then the in-memory copy | Prevents a post-clear append from resurrecting cleared history and makes a partial clear impossible to report as success |
| D18 | One provider-level semaphore (`OLLAMA_MAX_CONCURRENT`, default 2) bounds all simultaneous generation calls; chat waiters are bounded by `CONVERSATION_MAX_WAITING` (default 2) — beyond it the request is rejected before doing any work | Makes the "at most one job + one chat" overlap explicit and configurable; the queue worker always finds a free slot (chat uses ≤ 1), and waiting requests (each holding a typing indicator) cannot pile up unbounded |
| D19 | Throttled and at-capacity requests get at most one model-free notice per user per 5 minutes (the same gate as the reply hint); a same-scope in-flight request is still skipped silently | Bounded, honest feedback instead of silence, without turning every repeated event into noise — the typing indicator already shows in-flight work |
| D20 | Delivery stops at the first failed chunk and every stage reports the truthful `delivered=`/`persisted=` state; failures are logged once (typed + redacted, with chunk numbers) | A partial delivery can never grow duplicates or arrive mangled; nothing is claimed as sent that was not, and persistence failures are never reported as durable |
| D21 | `split_message` is fence-aware: a cut inside a code fence is moved to a natural boundary and otherwise the fence is closed and reopened with its language tag; only a boundary ≥ limit/2 is used, else hard cut | Every chunk renders as valid Markdown and no chunk becomes absurdly small; order and the ≤ 1900-char limit are preserved |
| D22 | KB-grounded chat (conversation Phase 4, design step): mention chat may use one bounded retrieval→prompt path — **only moderator-approved `kb_docs`** may enter chat context; retrieved text is treated as untrusted data (sanitized, fenced, instructions inside never followed); context is bounded and at most two source links are shown, clearly labeled "possibly related (not verified)"; disabled, empty, irrelevant or failing retrieval ⇒ normal chat continues unchanged; under prompt-size pressure the optional KB block is dropped **before** conversation history is reduced | Answers can draw on the community's own approved knowledge without reopening the indirect-injection class: approval stays the only door into the corpus, the fenced untrusted-data stance matches analysis, and the no-op fallback keeps chat identical when retrieval adds nothing. Explicitly revises RAG.md's display-only stance for this one bounded path (historical rationale preserved there) |
| D23 | Multi-guild operation is explicit but isolated: explicit target threads must be in the interaction guild and pass the channel allowlist; KB/related/insight/solution reads are guild-scoped; migration 4 adds `kb_docs.guild_id` and `approved`; auto thread fingerprints are `approved=0` and display-only | Keeps the product's small multi-guild deployment viable without making cross-guild leakage or unreviewed fingerprints an implicit behavior; a single-guild restriction would break the documented deployment model, while per-guild filtering reuses the existing schema/repository patterns |
| D24 | Agent capabilities are explicit typed application code, not model tools: a `Skill` declares ID, input/output models, permissions, timeout/output caps, safe error policy, and read-only status; the registry rejects arbitrary callables, duplicates, invalid metadata, and non-read-only skills; Phase 1 registers only `kb.search` (approved-only, guild-scoped) and `insights.community` (moderator, guild-scoped) | Keeps the model unable to invent, select, or invoke capabilities while reusing the existing repository/insights services. Phase 2A now supplies the backend approval state machine; public-action skills/executors remain Phase 2B work |
| D25 | Public/privileged actions use a backend approval state machine before any future side effect: an action stores action type, guild, target, content version and SHA-256 hash (never content), requester and expiry; only a trusted human actor with the `decide` permission can approve/reject; requester self-approval is rejected; decisions are conditional `pending` transitions; one execution claim revalidates state, expiry and exact binding immediately before the side effect, is unique by approval and idempotency key, and records started/executed/failed outcomes; all transitions write structured audit rows and failures fail closed | Prevents model output or a stale approval from authorizing a modified target/content; the conditional update closes concurrent decision races (also applied to the existing solution approve/reject workflow), and the claim table prevents duplicate side effects. Phase 2A deliberately registered no executor, command, or model tool |
| D26 | Content Studio publishes only through Phase 2A, immediately: drafts and immutable versions live in migration 6 tables; the **current version author** is the approval requester, so that author cannot approve their own version and another moderator must approve the exact target + version; material edits/target changes create a new version and cancel the old approval; publication rechecks human authority, guild/channel allowlists, fresh Discord member rights, bot send permissions, approval state/expiry/binding, then claims execution before one adapter send; recovery can only record a message proven by its deterministic nonce (a stuck `executing` claim is left intact otherwise) | Keeps one approval system and closes model-controlled or stale approval paths. Persisting reviewable text is necessary for editing/history, while approvals still store only a hash. A lost/ambiguous send is never retried blindly; the worst case is a safe manual follow-up, not a duplicate post. Scheduling is deliberately omitted |
| D27 | Community Pulse is a deterministic read model, not a model tool: it reads only guild-scoped stored summaries/KB rows, is gated by the existing minimum-data threshold, separates observations (facts in rows) from recommendations (explicit estimates with evidence, action, expected outcome, uncertainty), and derives stable recommendation ids from an observed key so reruns are reproducible. It never profiles members, invents engagement metrics, or asserts causation. | Correlations in small community data are weak; labeling observations, estimates, and uncertainty separately keeps the feature honest and auditable. Hash ids let a human convert the *current* recommendation while a stale id is rejected instead of trusting caller/model text |
| D28 | Knowledge candidates reuse the existing `solutions` lifecycle and no new approval mechanism: candidates are `solutions(state='proposed')` with source hash/summary/kind; duplicate and contradiction hints are deterministic lexical signals labeled unverified; only a trusted human moderator with `decide` may review; approval is the existing conditional `proposed → approved` + insert-new-`kb_docs` transaction (never an update to an existing approved solution). Summary-backed candidates are stale when their source is no longer latest. Thread expiry preserves approved `kb_docs` copies; `/knowledge-purge` is the explicit one-document purge and `/forget` the full-thread purge; audit rows are never swept. | Reusing the proven lifecycle avoids two sources of truth and keeps approved-only retrieval intact. Conditional transitions make concurrent review safe; insert-only publication means a second answer adds a document instead of silently replacing reviewed knowledge. Preserving approved copies through expiry prevents automatic retention from destroying knowledge a human explicitly approved |
| D29 | Approved knowledge is deleted only by an explicit, guild-scoped human action: `/knowledge-purge <doc N>` requires the allowlist, a fresh moderator check, a trusted human `decide` actor and the document's stored guild; the row delete, FTS trigger and audit insert share one transaction (audit failure rolls the delete back). Audit stores ids/kind/source ref/body length only, never title/URL/body. Audit rows are append-only with no automatic retention; free-text notes are not copied into audit metadata. Migration blocks roll back to the previous `user_version` on failure and startup closes the failed connection. | Automatic expiry must not silently destroy approved knowledge, but privacy requests need a targeted escape hatch after source threads disappear. A one-document purge is narrower and safer than reviving thread deletion, and transactional audit makes the irreversible action accountable. Indefinite audit retention is appropriate for a local, low-volume approval/deletion evidence trail; deleting it automatically would defeat its purpose, so no retention setting was added |
| D30 | Missions are deterministic, read-only plans over the existing skill registry: a mission mode maps to a fixed ordered plan (community: pulse → insights → KB search; research: web research → KB search; draft_prep: KB search → pulse, plus optional web research), the model never chooses a step or skill, every step is bounded by timeout/output caps, cancellation is cooperative between steps, every step result is persisted with evidence references and a trace id, an idempotency key is unique per guild, and startup recovery marks non-terminal missions `failed`/`interrupted` with their unfinished steps cancelled. Mission commands are moderator-only and guild-scoped. | Multi-step orchestration must not become an unconstrained autonomous agent on a local CPU: fixed plans keep runtime, cost and auditability predictable, reuse the D24 read-only contract as the only capability surface, and make a restart's outcome honest instead of leaving rows `running` forever |
| D31 | Web research is a configured, search-API-only capability: it calls Brave or Tavily (never a model tool), performs no page fetching (avoiding an SSRF path), rejects non-public/non-http(s)/credential-bearing URLs, and sends only the research query. Model synthesis is instructed and post-processed to strip URLs so every citation comes from provider results; synthesis failure falls back to an extractive report. Disabled or missing credentials produce a persisted `unavailable` state, never fabricated sources. Completed reports can seed a Content Studio draft with stored provenance but cannot submit, approve or publish. | Citations must be trustworthy and the feature must degrade honestly when offline/unconfigured. Search-only keeps the trust boundary to one provider API; URL stripping prevents the model from inventing citation targets, while the extractive fallback guarantees a usable evidence list without the model |
| D32 | Problem Radar is a deterministic read-only projection over Community Pulse: it reports recurring questions/errors, open threads and approved-knowledge gaps with the underlying counts as evidence, derives low/medium/high confidence from sample size, labels uncertainty and a recommended human action, and never profiles members or attributes causation. It shares Pulse's minimum-data gate and guild scope and stores nothing new. | The value of a radar is trustworthy evidence, not a second scoring system; reusing Pulse avoids divergent definitions, and count-derived confidence keeps the labels auditable and cheap on an 8 GB CPU machine |
| D33 | Agent evaluation is offline-only and deterministic: `/evaluate` exercises the typed registry contract, invalid input, unknown skills, permissions, guild/channel scope, redaction, image validation, migrations, approval binding and database isolation against temporary databases, persists a guild-scoped report plus audit, and fails the report on any regression. The report states `offline_only=True` and `model_quality_evaluated=False`; it never calls Discord, Ollama or external providers. | A project that cannot honestly distinguish "the plumbing is correct" from "the model is good" will overclaim. Temporary databases make reruns safe and keep evaluation away from user data; failing the report on contract regressions makes it a real gate rather than a demo |
| D34 | Content planning is draft-only and guild-scoped: event plans are deterministic templates, calendar entries are informational rows that schedule nothing, and contextual replies are one bounded model call over a pasted excerpt with mentions neutralized; none of them sends anything to Discord. State transitions are one-way and conditional (`draft→archived`, `planned→cancelled`, `draft→dismissed`) so repeated commands cannot silently "succeed", and only trusted human moderator actors with `decide` may create or dismiss. | Announcements and replies are the highest-risk surface for accidental public action; keeping every planning artifact reviewable and inert preserves the human-approval rule (D25/D26) while still giving moderators useful prep work. Conditional transitions make idempotency and audit honest |

## Known limitations (living list)

- Duplicate detection is lexical (FTS5 BM25), not semantic; paraphrased duplicates may be missed (documented in RAG.md).
- `gemma4:e2b` output quality is bounded by size; all model output is validated and labeled as suggestions, never as fact.
- Windows-first: paths use `pathlib`; Linux/macOS untested but intended to work.
- Live Discord behavior (gateway, permission edge cases) is unit-tested through duck-typed fakes; manual live sessions have since exercised slash commands, jobs, and mention chat (`data/logs/copilot.log`), and restart persistence + `/clear-conversation` have been observed working in live use.
- Test suite is mock-only by design; the single live-Ollama integration test is opt-in and was not run in the recorded log above.
- Mention chat turns persist locally in SQLite scoped per (guild, channel, user), bounded by `CONVERSATION_RETENTION_DAYS` (default 7) and `CONVERSATION_MAX_STORED_TURNS` (default 40); `/clear-conversation` deletes the caller's own turns immediately. While the database is unavailable, chat continues with in-process (volatile) context only and logs the degradation.
- Chat runs outside the queue with its own single in-flight gate: one chat generation can overlap one queued job, bounded by `OLLAMA_MAX_CONCURRENT` (default 2); at most `CONVERSATION_MAX_WAITING` chat requests may wait for the chat slot, and anyone beyond that gets one rate-limited notice. On a 1-CPU model the overlap shows up as latency, not failure.
- A reply to the bot is only readable when Discord exposes its text (an @mention); otherwise the bot sends a rate-limited "mention me" hint rather than guessing.
- Live Discord chat behavior and basic image interpretation passed the 2026-10-19 smoke test, and restart persistence + `/clear-conversation` have since been observed working; long-reply chunking, the throttle/busy notices, model-down recovery, and the hint path remain live-unverified.
- KB-grounded chat (D22, conversation Phase 4) is **implemented + unit-tested but not live-verified**: mention chat may attach one bounded, fenced `<kb>` block built only from approved `kb_docs` (default-on via `CONVERSATION_GROUNDING_*`), fail-open when retrieval errors, with at most two "possibly related (not verified)" source links and a `grounded=N` reply log; live smoke is DEPLOYMENT.md step 19 (not yet run).
- Retrieval **quality against a real corpus remains unmeasured** (lexical BM25 recall for paraphrases is a known limit), and the `<kb>` fence is hardening, not absolute prompt-injection prevention — the persona's untrusted-data rules are the primary control (fence-integrity cases are unit-tested).
- Program Phase 1 began as an internal foundation: the original two adapters were later extended by the host-agent work. All eight specialist roles now map to at least one registered read-only skill (`synthesis.brief`, `research.web` when configured, `content.brief`, `pulse.community` / `insights.community` / `radar.community`, `kb.search` / `knowledge.candidates`, `moderation.assess`, `triage.analyze`, `quality.checks`). The moderation skill is classification-only, `content.brief` never persists or publishes, `quality.checks` reuses the offline evaluation checks without writing a report, and screenshot vision remains on the mention-chat path after a real capability check. `/agent` exposes all six host modes; live execution is still covered by the runbook, not claimed here.
- Program Phase 2A remains backend-only except where Phase 2B now consumes it: the only approval-driven executor is Discord content publishing, with no generic approval command or model tool. Approval/audit rows are retained for audit evidence; expiry changes state but does not delete them. Existing thread/conversation retention does not purge approval records. Any future executor must construct `ApprovalActor` permissions from trusted backend checks (never model output) and call `begin_execution` immediately before its side effect.
- Program Phase 2B is **implemented + unit-tested but not live-verified**: the content path is disabled by default (`CONTENT_PUBLISHING_ENABLED=false`) and no real Discord post or migration of `data/copilot.db` was performed. Draft text is stored locally for review/history; approval rows still store only a SHA-256 hash. Generated text is prompted not to invent facts/links/dates/commitments and `needs_research` blocks approval, but there is **no automated fact checker**: a human must review the exact version before approving.
- Program Phase 3 is **implemented + unit-tested, not live-verified**: `/pulse`, `/pulse-draft`, and the candidate review commands were not exercised against a real Discord guild. Community Pulse is lexical/deterministic, so paraphrased questions or topics can be missed and overlap hints are not semantic verdicts; every recommendation is explicitly an estimate, and retrieval quality against a real corpus remains unmeasured. Recommendation evidence is read at request time and bounded; ids are recomputed, not stored.
- Candidate lifecycle reuses `solutions` rather than a new table, so a candidate and a manually proposed solution share the same id space and commands (`/knowledge-candidate-*` filter proposed rows by guild). Approved knowledge survives automatic thread expiry as a self-contained KB copy; `/knowledge-purge <doc N>` is the explicit one-document path (also for expired threads), `/forget` is the full-thread path. Audit rows (proposals, decisions, purges) are never swept. If a solution-backed document is purged, the `solutions` row stays approved as historical evidence and cannot be re-published by approving it again; a new candidate is required.
- Content publication is at-most-once per claim, not guaranteed delivered: a timeout/5xx leaves `executing`; `/content-recover` scans the last 100 target-channel messages for the deterministic nonce and records success only on an exact match. Otherwise the claim stays stuck and an operator must inspect Discord; it is never retried blindly. Scheduling is deliberately out of scope.
- Mission orchestration (program Phase 3.2) is **implemented + unit-tested but not live-verified**: plans are fixed per mode and read-only, so a mission cannot investigate a free-form hypothesis or call a new capability; cancellation is checked between steps (a single in-flight skill call finishes or times out first); startup recovery closes interrupted missions as `failed`. Live progress rendering and restart recovery still need the runbook's mission section.
- Web research (program Phase 3.3) is **off by default and not live-verified against any provider**: tests use a fake search provider. Search quality, rate limits, and provider-specific response quirks are unmeasured; there is no page-content fetch, so summaries rely on provider titles/snippets plus the local model. Citations are only as good as the provider results; an extractive fallback is used when model synthesis fails.
- Problem Radar (program Phase 3.4) is **implemented + unit-tested but not live-verified**: it is lexical and count-based over stored summaries/KB rows, so paraphrased questions can be missed and confidence reflects sample size, not truth; it never measures engagement or causation.
- Agent evaluation (program Phase 3.5) is **offline-only by design**: it validates contracts, safety and isolation, not answer quality, prompt effectiveness or latency. A passing report must not be read as "the model is good". Reports are persisted per guild for later review.
- Content planning (program Phase 3.6) is **implemented + unit-tested but not live-verified**: calendar entries are informational rows (nothing is scheduled or sent), event plans are deterministic templates, and reply drafts are generated from a pasted excerpt, mention-neutralized, and never posted automatically. Generated drafts still require human review before any manual use.
- Consolidated live E2E was **not run** in the 2026-10-23 implementation phase, by instruction. [`E2E_TEST_RUNBOOK.md`](E2E_TEST_RUNBOOK.md) lists every deferred check; until it is executed, all new program-phase rows remain `[~]`, not `[x]`.
